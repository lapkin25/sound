# Патч TRIOMAT: решение по layout — вариант Б (v0.2)

Файл патча для `triomat_canonical.md` и TTB-Spec. Основание: сверка чек-листа
раздела 8 TTB с каноном (реплика «сверимся со спекой»), решение владельца — вариант Б.

## 1. Решение

Layout (порядок обхода элементов: C = row-major, F = column-major) **не хранится
в формате** и не входит в заголовок. Файл TRIOMAT1 всегда несёт payload в C-порядке.
F-упаковка — ответственность слоя моста, не формата.

Альтернатива (вариант А — флаг `layout` в заголовке) отклонена по двум причинам:

1. **Детерминизм.** Одна и та же матрица допускала бы два корректных файла
   (C и F), байтово различных. Канон перестаёт быть каноном: побитовое сравнение
   файлов перестаёт отвечать на вопрос «это одни данные?» без парсинга.
2. **Закрытый формат.** Флаг ломал бы закрытый набор полей заголовка и требовал
   переклейки всех golden-записей (новое имя формата или версия).

## 2. Правки в triomat_canonical.md

### 2.1 Новый подраздел после «Payload»

> **Layout и каноничность**
>
> Payload всегда записывается в C-порядке (row-major), независимо от layout
> источника. Свойство канона: F-источник и C-источник одной и той же матрицы
> обязаны давать байт-в-байт одинаковый файл. Слежение за layout — обязанность
> слоя моста (`pack_octave`/`unpack_octave`), не формата. Транскодинг F↔C на
> границе журналируется как событие моста.

### 2.2 Правка таблицы ошибок

Строка «TypeError | dtype вне закрытого списка» заменяется на:

| Код | Когда |
|---|---|
| `MalformedDtype` | dtype вне закрытого списка (Float32 не существует в SCore) |

Мотивация: файловый `TypeError` коллизирует с транспортным `TypeMismatch`
из закрытого набора TrioError. Переименование касается только файлового слоя
TRIOMAT; рекордный `TypeError` в SCore/STRUCT остаётся — разные пространства имён.

### 2.3 Контракт `read_matrix`

`read_matrix` возвращает layout-компонент, **всегда равный 0**: чтение из файла
возвращает C-порядок по построению. Сигнатура сохранена ради совместимости
существующих вызовов; значение служит явным подтверждением канона, а не данными.

## 3. Правки в TTB-Spec (слои моста)

### 3.1 pack_octave / unpack_octave

Формализация границ моста:

- `pack_octave(m) -> TRIOMAT1` — приём column-major матрицы Octave,
  транскодинг в C-порядок внутри моста, файл канонический;
- `unpack_octave(bytes) -> OctaveMatrix` — обратный транскодинг на принимающей
  стороне Octave: каноническая ловушка «читать через `reshape(data, cols, rows)'`»
  остаётся в силе и применяется к payload C-порядка;
- событие транскодинга фиксируется в журнале моста (без изменения формата файла).

## 4. Правки чек-листа (test_bridge v0.2, секция T2)

Три строки, кодифицировавшие хранение layout, заменяются:

- ~~`check("Roundtrip F: layout=1, значения идентичны", layout2 == 1 and ...)`~~
- заменить на: `check("Roundtrip F: файл всегда C-порядка (layout=0), значения идентичны", layout2 == 0 and ...)`
- добавить (сильный чек канона): `check("Канон: F-источник и C-источник дают байт-в-байт одинаковый файл", write_c_bytes == write_f_bytes)`
- строка «C- и F-байтовые порядки различаются» исключается: под вариантом Б
  различие байтов означало бы нарушение канона.

Статус: чек-лист v0.2 прогнан против патчнутой реализации — 26/26 PASS.

## 5. Последствия для golden-записей

Ноль переклейки: magic `TRIOMAT1`, структура заголовка и закрытый набор флагов
`{stub, lossy, trusted}` не меняются. Все существующие golden-файлы остаются
валидными; свойство из §2.1 является усилением контракта, а не сменой формата.
