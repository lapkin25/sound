# Спецификация Math Machine — v0.1

Слой доказательств над sound-машиной.
Составлен из решений диалога; решения D1–D4 подтверждены автором проекта.
Статус: v0.1, согласована модель данных и базовые семантики.
Связь: надстраивается над форком спецификации prfon v0.4-fork1 (§2 — звуковой слой).

## §0. Место в стеке

Три слоя, снизу вверх:

1. **PR-язык** (прямая дорога) — семантический эталон: примитивно-рекурсивные
   программы, интерпретатор `run_pr` v0.3.
2. **Sound-машина** (звуковая дорога) — ленточный исполнитель с протоколом шагов,
   компилятор `pr2sound`, сверка в три уровня (`check`, `cross-check`, детерминизм).
3. **Math Machine** — скрипты-доказательства. Каждый скрипт — последовательность
   утверждений, каждое из которых машина проверяет независимо.

Math Machine не вводит новой вычислительной модели: её исполнители — уже
построенные дороги. Новизна слоя — в формате утверждений и правиле независимости.

## §1. Сущности

### 1.1 Value — значение

Целое неотрицательное число произвольной точности. Два представления на двух
уровнях абстракции (решение D2):

- **Уровень абстракции** (язык скриптов): десятичная запись, доверенная база.
  Скрипты и утверждения оперируют десятичными числами; их разбор и сравнение —
  доверенные операции, как builtin.
- **Подуровень машины** (звуковая дорога): унарная лента. Конвертация
  «десятичная запись → лента» — деталь реализации звукового слоя, подлежащая
  собственной сверке средствами самой машины (а не доверенная аксиома скрипта).

Так граница доверенной базы не уничтожается, а локализуется: на каждом уровне
доверено только то, что ниже него.

### 1.2 Target — объект доказательства

```json
{"lang": "pr", "text": "<текст программы>", "hash": "<sha256>", "entry": "add(5,3)"}
```

- `lang`: `"pr"` или `"sound"`.
- `text`: полный текст программы. Хранится всегда (урок живучести: текст
  переживает пересылку, хеш без текста бесполезен).
- `hash`: sha256 от **нормализованного** текста. Нормализация v0.1: построчно
  отрезать концевые пробелы, отбросить пустые строки, склеить переводами строк
  `\n`.
- `entry`: точка входа в канонизированном формате (`entry add(5,3)`, без
  двоеточия).

**Идентичность** программы определяется нормализованным текстом; hash —
контрольное поле. При несоответствии `sha256(norm(text)) != hash` утверждение
помечается `failed` с причиной `identity-mismatch` (утверждение внутренне
противоречиво, проверять нечего).

### 1.3 Assertion — утверждение

Атомарная единица скрипта.

```json
{
  "id": "A1",
  "kind": "value | trace | invariant | lemma",
  "target": {…},
  "claim": {…},
  "evidence": null | {…},
  "status": "pending"
}
```

Виды (v0.1):

- **`value`** — «target на entry возвращает claim.value».
  Проверка: полный прогон соответствующей дороги, сверка значения.
  Дорога выбирается по `lang`; скрипт не может требовать конкретную дорогу —
  проверяющий волен прогнать обе и сверить их между собой (это сильнее).
- **`trace`** — «прогон target на entry порождает протокол с sha256 =
  claim.protocol_sha256». Проверка: переразыгрывание шагов исполнителем и
  сверка хеша канонической сериализации протокола.
- **`invariant`** — «на протоколе от target@entry выполнено свойство
  claim.invariant». Проверка v0.1: внешний интерпретатор предикатов над шагами
  протокола; протокол пересчитывается проверяющим заново (правило независимости —
  §2), а не берётся из чужого файла. Конкретный синтаксис предикатов — открытый
  вопрос MM-1.
- **`lemma`** — утверждение, ссылающееся на другие утверждения по `id`:
  `claim.ref = ["A1", "A3", …]`. Проверка: **разворачивание** (решение D1) —
  проверяющий заново и независимо проверяет каждое ссылочное утверждение с нуля.
  Результаты и статусы ссылок не используются. Лемма верифицирована, когда все
  её ссылки верифицированы в рамках этой же проверки.

### 1.4 Certificate — сертификат

Протокол исполнения в канонической форме `.sound.jsonl` (одна запись JSON на
шаг). Хеш сертификата — sha256 от байтов файла в канонической сериализации.
Сертификат — первоклассная структура данных (§4, метафора D4); компактные формы
(дельта-сертификаты, проверяемые фрагменты) — отложены до встречи со стеной
унарного кодирования (открытый вопрос MM-3).

### 1.5 Script — скрипт

```json
{
  "spec": "math-machine v0.1",
  "name": "fact-row",
  "assertions": [ … ]
}
```

Результаты проверки пишутся в отдельную таблицу результатов (не внутрь
утверждений): id → `{status: "verified"|"failed"|"unsupported", reason?,
steps?, time?}`. Число шагов, затраченных на проверку, — наблюдаемая величина;
метрика проверки входит в результат.

## §2. Правило независимости

Проверка утверждения A не может использовать результаты и статусы других
утверждений — ни их значения, ни их `verified`. Проверено сто раз — проверяется
сто первый раз с нуля.

Следствия:

- Таблица результатов самодостаточна: упади один пункт — остальные не
  обесцениваются.
- В сырье (evidence, target, сертификаты) ссылаться можно — это данные, не
  результаты. Но для `invariant` протокол пересчитывается, а не доверяется файлу.
- Леммы — единственный разрешённый вид зависимости, и он разворачивается до
  независимых проверок (D1). Цена — повторные вычисления; это осознанный выбор
  честности против производительности (открытый вопрос MM-4 — кэширование
  на уровне проверяющего, не скрипта).

## §3. Доверенная база (сводка, решение D2)

| Операция | Уровень | Статус |
|---|---|---|
| Разбор десятичной записи, сравнение значений | абстракция | доверенная |
| Лексер/парсер PR и sound-языков | абстракция | доверенная (как builtin) |
| Исполнение дорог (run_pr, run_sound) | машина | сверяется протоколом |
| Конвертация десятичная → унарная лента | подуровень машины | деталь sound-слоя, сверяется средствами машины |
| sha256 | абстракция | доверенная |

Всё, что ниже уровня абстракции, должно быть проверяемо средствами вышележащих
слоёв — так формулируется требование на будущие версии.

## §4. Язык инвариантов — направление (решение D4)

Принята метафора: **язык доказательств относится к языку программ, как алгоритм
к структуре данных**. Протокол исполнения — структура данных; инвариант —
программа, которая по ней ходит.

Отсюда на v0.2: язык предикатов над шагами протокола реализуется как PR-программы
(доказательства пишутся на том же языке, что и доказываемое). Для этого протокол
должен получить представление, доступное PR: числовое/ленточное кодирование
записей шагов. Это стыкуется с открытым вопросом №5 форка (позиционное
кодирование лент) — решение по MM-1 и №5 нужно принимать совместно.

На v0.1 инварианты проверяет внешний интерпретатор; это мост, а не цель.

## §5. Открытые вопросы

- **MM-1. Синтаксис инвариантов v0.1.** Минимальный язык предикатов над шагами
  протокола: доступ к полям записи (опкод, ленты, указатели), кванторы по шагам?
  Предложение: начать с ограниченного — предикат над одной записью и
  квантор «на всех шагах» — и проверить на фактическом инварианте prec-цикла.
- **MM-2. Общий хеш-формат протокола.** Каноническая сериализация jsonl
  определена как байты файла; при пересчёте протокола двумя разными
  исполнителями байты обязаны совпадать — требуется зафиксировать порядок полей
  и формат чисел в записи.
- **MM-3. Компактные сертификаты.** Полный протокол mul(6,7) — 111 833 записи.
  Форматы сжатия (интервалы, дельты, проверяемые фрагменты) отложены до стены
  факт(9) — проектировать без измеренного противника запрещено (урок №4).
- **MM-4. Кэш проверяющего.** Правило независимости запрещает кэш в скрипте,
  но не в проверяющем: можно ли кэшировать результаты пересчёта между
  утверждениями в рамках одного запуска? Предложение: да, с журналом — кэш
  помечается в таблице результатов, проверяемый эффект — только скорость.
- **MM-5. Стратегия дорог для `value`.** Обе дороги или одна? Предложение: по
  умолчанию обе с взаимной сверкой, отклонение — только при явной метке в
  утверждении.

## §6. Первый скрипт (план вживой проверки)

`fact-row`: пять утверждений `value` (fact(5)=120, fact(7)=5040, fact(9)=362880,
fact(20)=2432902008176640000 на прямой дороге; add(5,3)=8 на обеих) + одно
`trace` (add(5,3), протокол из форка) + одна `lemma` над value-утверждениями.
Ожидаемый результат: все verified; число шагов проверки совпадает с числом шагов
прогона (транзитивность независимости).

## §7. Журнал решений

- **D1** (диалог, сессия MM-модели): леммы разрешены; зависимость — по тексту
  ссылки, разворачивание при проверке, без переиспользования результатов.
- **D2** (диалог): два уровня абстракции — десятичный (доверенный) и унарная
  лента (подуровень машины, сверяемый). Граница доверенной базы локализована,
  не уничтожена.
- **D3** (диалог): идентичность программы — sha256 от нормализованного текста;
  несоответствие — `failed`/`identity-mismatch`.
- **D4** (диалог): язык инвариантов — PR-программы (направление); метафора
  «доказательство : программа = алгоритм : структура данных» принята как
  принцип дизайна сертификатов.
