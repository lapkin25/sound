# Trio — реферат

версия спецификации: `sound-0.5` · 2026-11-22 · слой 3 архитектуры Sound

---

## 1. Идея: реплей, а не доверие

Trio — рантаймы-дублёры. Их задача — **воспроизвести** записанное вычисление на
независимой платформе и сверить результат байт-в-байт. Дублёр не доверяет
платформе и не доверяет следу: он проверяет след воспроизведением.

Фундаментальное свойство: **реплей не интерпретирует язык.** Дублёр не содержит
ни разбора, ни типизации, ни выбора порядка — всё это уже решено транскриптором
и зашито в граф. Дублёр — это только арифметика словаря и ворота платформы.
Сверка — воспроизведением, а не доверием.

## 2. Состав: три дублёра

| Дублёр | Ворота платформы |
|---|---|
| Octave | `num2hex` |
| C | punning |
| Wolfram Language | бинарный экспорт |

Ворота — это способ вывести значение любой операции словаря в канон TRIOMAT
средствами платформы, без единой собственной арифметики сверх словаря. Три
независимых рантайма нужны, чтобы расхождение нельзя было списать на
особенности одной платформы: совпадение трёх независимых реализаций —
сильное свидетельство корректности канона.

## 3. Протокол реплея

Дублёр получает **только снапшот ANF/1** — ни Piano-исходника, ни компилятора.

```
1. вычеркнуть из графа неисполненные узлы
2. вычислить каждый узел журнала собственной арифметикой дублёра
3. вывести результат через ворота платформы в канон TRIOMAT
4. сверить hex-строками с записанным в журнале
```

Правила:

- `set` — источник истины реплея: присвоенное значение в журнале — эталон.
- Расхождение локализуется до конкретной строки журнала (`t5` — конкретная
  строка), а не «особенность платформы».
- Снапшот с незнакомыми версиями `dict`/`canon` не парсится вовсе —
  версия-миграция выполняется заранее, на стороне корпуса.

## 4. Чего дублёр не делает

- Не читает Piano-исходник.
- Не компилирует и не перепроверяет типизацию.
- Не выбирает порядок исполнения — порядок уже канонический.
- Не содержит случайности: генератор по сиду — обязанность слоя 1/2.
- Не вычисляет ничего, кроме операций словаря core/2.

## 5. Роль в схеме «вход как снапшот»

Вход подаётся параметрам до компиляции и живёт в секции `environment`. Для
дублёра это означает:

- вход не требует никакого ввода-вывода — он уже в файле;
- две партии данных — два снапшота, два следа, два отпечатка;
- **граф инвариантен к входу**: один исходник при разных входах даёт один и
  тот же граф байт-в-байт, различаются только `environment` и журнал. Дублёру
  неважно, три шага или тридцать — он вычёркивает из графа неисполненное и
  сверяет построчно.

## 6. Цепочка снапшотов: эволюция состояния

Долгоживущая система моделируется не «программой, которая живёт», а
последовательностью снапшотов: снапшот № k вычисляет новое состояние, оно
подаётся как факт (или параметр) в снапшот № k+1. Каждый шаг — свой след и свой
отпечаток; вся история системы — верифицируемая цепочка. Для модельных задач
это даже честнее живого состояния: легко откатиться и перегнать шаг с другим
правилом.

## 7. Что дублёр покупает системе

- **Проверяемость без доверия.** Совпадение реплея — не «мы поверили Octave»,
  а «независимая арифметика воспроизвела каждый узел».
- **Отпечаток как идентичность.** Отпечаток (SHA-256 цепочкой по журналу)
  делает экземпляр вычисления самотождественным: совпал — тот же след.
- **Откат без драмы.** Ошибка в следе (как была поймана схема fold2 без snoc)
  обнаруживается валидатором и реплеем до того, как станет корпусной нормой.
- **Кросс-платформенная честность канона.** Политики Int64 (модуль 2^64),
  NaN (переворот знака, payload сохраняется, первый NaN-операнд побеждает) и
  денормалы (полная IEEE) обязаны давать одинаковые hex-строки на всех трёх
  платформах — иначе канон не считается принятым.
