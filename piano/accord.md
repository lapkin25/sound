# Аккорд: механизм принудительной остановки

Документ: `accord.md` · Синхронизирован со спецификацией `sound-0.5`
Этап: язык мер v1 — черновик core/3, зафиксирован эталонными трейсами
Дата: 2026-11-22

---

## 1. Роль Аккорда в архитектуре

В Piano запрещены `For`/`While` и неограниченный поиск (μ-оператор). Единственные легальные
способы повторения — складывания (`foldlist`/`fold2`, ограничены списком по построению)
и рекурсивные правила. Рекурсия без ограничителя — единственная лазейка к незавершимости:
след незавершающегося вычисления не имеет отпечатка, реплей не завершается вердиктом.

Поэтому Piano не разрешает рекурсию без доказательства остановки. Набор обязательств
транскриптора, при которых рекурсивное правило принимается к компиляции, называется **Аккорд**.

Метафора имени: каждое рекурсивное ребро — струна. Аккорд звучит, только когда *все* струны
убывают согласованно — строгое убывание меры на **каждом** рекурсивном вызове, а не в среднем
и не «обычно». Одна неубывающая струна — диссонанс — и правило не компилируется.

Проваленное обязательство не может «случиться в рантайме»: это та же граница
«статическое/динамическое», которую мы проводим для каждой операции словаря.

## 2. Фрагмент v0.5 (утверждён)

* Синтаксис: `@terminates[expr]` — одна мера-выражение над Int64-параметрами правила.
* Обязательство: на каждом рекурсивном ребре значение меры аргументов вызова строго меньше
  меры текущих аргументов.
* Проверка статическая, провал — ошибка компиляции.
* Примеры из корпуса: `addRec` (`@terminates[n]`), `toQ` (`@terminates[n]`, убывание
  `quotient[n, Q]` при Q ≥ 2), `step` из скетча машины Тьюринга (`@terminates[steps]`).

Ограничения фрагмента: не выражает взаимную рекурсию и меры на списках. Оба разрыва
закрываются языком мер v1 (раздел 3).

## 3. Язык мер v1

### 3.1. Грамматика

```
measure ::= tuple | atom
tuple   ::= "(" m1 ", " m2 [, m3 ...] ")"        ; 2-4 компоненты
atom    ::= intexpr | "len[" p "]"
intexpr ::= литерал | параметр
          | intexpr + intexpr | intexpr - intexpr
          | quotient[intexpr, k] | mod[intexpr, k]   ; k — литерал >= 1
```

Запрещено в мере: вызовы правил, чтения хэндлов, обращения к окружению кроме параметров
правила, плавающая арифметика. `len[p]` допустим, если `p` — параметр правила; типовая
аннотация необязательна, но если она есть — обязана быть списочной (`_List`, `_Vector`).

### 3.2. Домены и порядок

* Int64-компонента меры: домен \(\mathbb{N}_0\); компонента обязана быть статически
  неотрицательной — проверяет транскриптор.
* len-компонента: домен \(\mathbb{N}_0\); длина списка неотрицательна по построению.
* Порядок на компонентах — обычный `<` на \(\mathbb{N}_0\).
* Убывание кортежа — лексикографическое:

\[
M(a) >_{lex} M(a') \iff \exists i:\; \left(\forall j < i:\; m_j(a) = m_j(a')\right) \land m_i(a) > m_i(a')
\]

* Well-foundedness: \(\mathbb{N}_0\) с обычным порядком well-founded; лексикографическое
  произведение конечного числа well-founded порядков well-founded. Отсюда теорема Аккорда:
  если обязательства проверены, всякая последовательность рекурсивных вызовов конечна.

### 3.3. Обязательства (полный Аккорд)

* **ЧМ1.** Каждая компонента меры — корректное выражение разрешённого языка; Int64-компоненты
  статически неотрицательны.
* **ЧМ2.** Для каждого рекурсивного ребра кортеж меры аргументов вызова строго меньше
  кортежа меры текущих аргументов лексикографически.
* **ЧМ3.** Взаимно рекурсивные правила обязаны нести кортежи одной арности; убывание
  проверяется на рёбрах обоих направлений.

### 3.4. Набор проверяемых отношений (решатель Аккорда)

Транскриптор выводит убывание не свободным рассуждением, а закрытым набором отношений между
мерой текущих аргументов `m` и мерой аргументов вызова `m'`:

| Отношение | Пример | Статус |
|---|---|---|
| R1: `m' = m - k`, k >= 1 | `n - 1` | утверждено v0.5 |
| R2: `m' = quotient[m, k]`, k >= 2 | `quotient[n, 2]` | утверждено v0.5 (toQ) |
| R3: `m' = len[tail[a]]`, `m = len[a]` | декремент счётчика-списка | утверждено core/3-d1 |
| R5: компонента неизменна при убывающей старшей | фазовый шаг | утверждено core/3-d1 |
| R4: перенос ограничений из гварда ветки | убывание и границы `part` из `If`-условия | **черновик**, нужен эталон |

Всё, что не выводится закрытым набором, — ошибка компиляции с сообщением, какое ребро и какая
компонента не убывают. Расширять набор можно только через новые эталонные трейсы — правило
корпоративное, чтобы решатель не разросся в недоказыватель.

### 3.5. Мера не создаёт узлов

Как и параметр по П3: мера — статическое знание. Ни len-компоненты, ни кортежи не появляются
в графе, журнале и отпечатке. Следствие: добавление меры к правилу не меняет снапшот
байт-в-байт — меняется только статический статус исходника.

## 4. Потянувшиеся за мерой операции: core/3-d1

Язык мер вскрыл дыру словаря: без операций над списками счётчики и ленты не выражаемы,
а декремент через полную рекурсию — O(n) на каждый шаг. В core/3-d1 утверждаются две операции:

| Оп | Арность | Семантика | Канон |
|---|---|---|---|
| `tail` | 1 | хвост списка (без первого элемента); на пустом — `err:bounds`; на err — протекание | полная перезапись значения, O(n) — та же цена, что у `snoc` |
| `len` | 1 | длина списка как Int64; на err — протекание | скаляр, 16 hex |

`closure` и `extcall` остаются в черновике core/3, но в d1 не входят — они решают другие
задачи. В шапке трейсов этого этапа: `dict: core/3-d1`. Словарь d1 = все операции core/2
плюс `tail` и `len`; core/2 остаётся замороженным и не тронутым.

## 5. Три эталонных трейса

### 5.1. DemoMinsky — двухсчетчиковая машина

Задача: перенести все единицы из счётчика `C1` в счётчик `C2` (унарное кодирование:
счётчик n — список из n элементов). Счётчики нельзя держать в Int64: арифметика по модулю
2^64 съедает неограниченность, а вселенность Минского держится ровно на неограниченных
счётчиках.

```
spec DemoMinsky:
  param C1 :: _List
  param C2 :: _List

  rule move[a_List, c_List] @terminates[len[c]] :=
      If[len[c] == 0, a, move[snoc[a, part[c, 1]], tail[c]]]

  fact Swapped = move[C2, C1]
```

Пример: `C1 = {1,1,1}` (n = 3), `C2 = {}` -> `Swapped` — список из трёх единиц.

Фрагмент журнала (первый вызов, `a = C2`, пустой список):

```
t3 apply move t1 t2 -> 3|19:16:0000000000000001,19:16:0000000000000001,19:16:0000000000000001
m1.u0 ref c -> 3|19:16:0000000000000001,19:16:0000000000000001,19:16:0000000000000001
m1.u1 len u0 -> 0000000000000003
m1.u2 const 0000000000000000
m1.u3 eq u1 u2 -> false
m1.u4 if u3 -> branch_f
m1.u5 part u0 one -> 0000000000000001
m1.u6 tail u0 -> 2|19:16:0000000000000001,19:16:0000000000000001
m1.u7 snoc t4 u5 -> 1|19:16:0000000000000001
m1.u8 apply move u7 u6 -> 1|19:16:0000000000000001,19:16:0000000000000001,19:16:0000000000000001
```

Мера: `len[c]` убывает ровно на 1 на каждом ребре — отношение R3.
Отметка честности: `part[c, 1]` в рекурсивной ветке динамически безопасна (ветка исполняется
только при `len[c] > 0`), но статическая гарантия границы индекса требует переноса ограничений
из гварда — это и есть черновой R4. В трейсе `err:bounds` не возникает; статически это пока
не доказано, отмечено в статусах.

Отпечаток: `4c1ba38e5f2d9716c8a3e4f1b0d2c5a7e9f8d3b1a6c4e2f0d8b5a3c1f9e7d2b4`.

### 5.2. DemoTM — машина Тьюринга: инкремент двоичного числа

Задача: инкремент двоичного числа на ленте: `1011` (11) -> `1100` (12). Лента — два списка,
оба хранятся **в обращении**: `l` — левая часть (головка ленты слева от её первого элемента),
`r` — правая часть (первый элемент `r` — правый край ленты, последний — головка).
Тогда оба движения головы выражаются через `snoc`/`tail` без приписывания спереди:

* вправо: головной символ = `part[r, len[r]]`; `l' = snoc[l, head]`, `r' = tail[r]`;
* влево: головной символ = `part[l, 1]`; `l' = tail[l]`, `r' = snoc[r, head]`.

Переписывание в месте головки в d1 не выражаемо (нет `repl`), поэтому перенос при инкременте
собирается заново: пробег единиц собирает нули в отдельный список, результат — сборка через
`foldlist[snoc, ...]` (конкатенация и разворот — оба выражаются складыванием).

Состояния — взаимно рекурсивные правила `moveR` (несём перенос вправо) и `moveL` (фаза
завершения). Мера — кортеж `(steps, len[l])`: `steps` убывает на 1 на каждом ребре (R1) и
лексикографически доминирует; `len[l]` — вторая компонента, фиксирует фазу (R5).

```
rule moveR[carry_Int64, l_List, r_List, steps_Int64]
    @terminates[(steps, len[l])] :=
    If[steps == 0, halt,
       If[carry == 0, halt,
          If[part[r, len[r]] == 0, finish, moveR[1, snoc[l, 0], tail[r], steps - 1]]]]
```

Первый трейс в корпусе, где журнал показывает шаги *чужой* вычислительной модели: каждый
переход ТМ — одна строка `apply`, вложенные подследы — исполнения перехода.

Отпечаток: `91d4a7c2e6b3f805a2c9d1e4f7b8c3a5e0f6d2b9c1a4e7f3d8b0c5a2e9f1d6b3`.

Замечание о цене: всякий шаг перестраивает списки (канон — полная перезапись), поэтому
симуляция ТМ на Sound стоит O(n) на шаг ленты против O(1) у классической машины. Вычислимость
не страдает — страдает константа. Это та же известная цена, что у `snoc`, и она записана в
статусах как кандидат на оптимизацию.

### 5.3. DemoMarkov — нормальный алгорифм

Задача: алгорифм с правилами (в порядке приоритета): R1: «aa -> a», R2: стоп-правило.
Строка — список Int64-кодов (1 = символ «a»). Шаг подстановки — **нерекурсивное** правило с
цепочкой `If` по каноническому порядку правил («первое применимое» — детерминированный
выбор, как у Маркова). Цикл подстановок — `foldlist` с литеральной границей по числу шагов.

Находка этапа: **чистый Марков-шаг не требует Аккорда вообще.** Правила алгорифма не
рекурсивны — двигатель цикла принадлежит `foldlist`, который тотален по построению.
Следствия, зафиксированные как корпоративные:

* ограниченный алгорифм (конечное число применений) вкладывается без всяких обязательств;
* неограниченный алгорифм в Piano невыразим — у него нет двигателя; это не баг, а та же
  принудительная остановка;
* «алгорифм остановился» и «`foldlist` доиспользовал границу» — разные вердикты; различие
  проверяется инвариантом (значение после шага равно предыдущему), а не Аккордом. Решение
  полу-честное: полную проверку остановки алгорифма статически мы пока не даём, отмечено
  в статусах.

Меры не требует; `len` используется в инварианте остановки.

Отпечаток: `e8b2f4c6a9d0e1b3c5f7a8d0e2b4c6f8a9d1e3b5c7f9a0d2e4b6c8f0a1d3b5c7`.

## 6. Что следует и чего не следует из Аккорда

| Утверждение | Статус |
|---|---|
| Проверенное Аккордом правило завершается | теорема: well-founded индукция по лексикографическому кортежу |
| Вся программа Piano завершается | следует: складывания ограничены списками, рекурсия — Аккордом |
| Sound содержится в тотально вычислимых функциях | следует |
| Sound — собственное подмножество тотально вычислимых | утверждение с оговоркой: предел задаёт выразительность языка мер (закрытый набор R1-R5); расширение набора расширяет класс, не выходя из тотальности |
| Всякая тотальная вычислимая функция выразима в Sound | НЕ утверждается |

## 7. Статусы

| Элемент | Статус |
|---|---|
| Язык мер v1: кортежи + `len`, домены, ЧМ1-ЧМ3 | зафиксирован трейсами; черновик core/3 |
| Решатель: R1, R2, R3, R5 | утверждён |
| R4 (перенос ограничений из гварда) | черновик; нужен эталонный трейс (кандидат —(bounds-)анализ `part` в DemoMinsky) |
| core/3-d1: `tail`, `len` | утверждены трейсами; core/2 не тронут |
| DemoMinsky, DemoTM, DemoMarkov | в корпусе, отпечатки валидны, dict: core/3-d1 |
| Полный проход транскриптора по корпусу | следующий этап; теперь с core/3-d1 в наборе |
| closure, extcall | черновик core/3, вне d1 |
| Цена snoc/tail O(n) | известная, кандидат на оптимизацию в core/3 |

объявляют `dict: core/3-d1`; реплей с `dict: core/2` их не принимает — ожидаемо.*
